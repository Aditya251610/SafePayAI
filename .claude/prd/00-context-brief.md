## 2. Core flow (settled design)
1. Buyer signs a Mandate: merchant allowlist, max total (integer minor units, incl. fees), intent text, expiry, revocable, pre-authorized protection terms (e.g. auto-refund up to X if not delivered by day Y), policy_version pin, nonce, hash + server HMAC (demo-grade; not buyer-held-key).
2. Buyer types intent ("birthday gift for a runner under $60"). Agent (LLM) returns a structured cart (catalog item IDs + quantities only) from a small SEEDED catalog (~12 items, 3 virtual merchants settling to one sandbox merchant). Server re-prices from DB.
3. Deterministic mandate checks (hard-block: revoked/expired, merchant not allowlisted, total over cap, unknown SKU, quantity cap, currency mismatch, agent-stated price != DB). Advisory AI intent-fit check can only tighten (PASS / NEEDS_BUYER_CONFIRMATION / REJECT_WITH_REASON); it never clears a hard block.
4. Server creates PayPal Orders v2 order; buyer approves in PayPal (needs a real click in sandbox); server captures. Receipt shows reasons and a demo "Protected until day X" (NOT PayPal's real window).
5. Merchant adds tracking; carrier is SIMULATED (status held in OUR DB) with a demo-clock control; poller detects late/lost; buyer can also report a problem in free text (untrusted).
6. AI triage: classify text into enum {LATE, LOST, DAMAGED, WRONG_ITEM, NOT_AS_DESCRIBED, OTHER} + confidence; draft messages (regex gate: no URLs/amounts); read-only reviewer brief. Fail-closed to HUMAN_REVIEW on error/low confidence/schema failure. AI NEVER decides money.
7. Deterministic merchant policy (3 hardcoded, illustrative: refund cap ~$50, category exclusions, buyer velocity > 2 refunds/30 days -> human) checks against the mandate's pre-authorized terms. Inside the terms: refund offer; anything else needs fresh buyer approval (single-use signed link bound by proposal_hash).
8. Server runs 9 ordered checks, then PayPal Payments v2 refund with persisted PayPal-Request-Id; unknown/ambiguous results are reconciled by lookup, never blind retry. Merchant override = a NEW offer needing buyer approval.
9. Append-only, hash-chained audit log covers mandate, cart, order, refund (INSERT/SELECT-only DB role, triggers block UPDATE/DELETE, "verify chain" endpoint).
10. States: PROTECTED, MONITORING, PROBLEM_DETECTED, TRIAGED, OFFERED, HUMAN_REVIEW, APPROVED, REFUNDING, RESOLVED_REFUNDED, RESOLVED_RESHIP, DECLINED, CLOSED.

## 3. Verified PayPal SANDBOX facts (our own spike, 2026-10-10; V)
- Auth: OAuth client-credentials token works; expires_in ~32,000 s (~9 h); invalid token -> 401.
- Orders v2: create works; same `PayPal-Request-Id` replay returns the SAME order. Order starts PAYER_ACTION_REQUIRED; buyer must approve via the PayPal sandbox page (redirect to return_url with `token` and `PayerID`); then APPROVED; capture returns 201 COMPLETED.
- `custom_id` and `invoice_id` set on the purchase unit survive onto the capture (so the mandate can be traced).
- Tracking: `POST /v2/checkout/orders/{id}/track` (capture_id, tracking_number, carrier OTHER + carrier_name_other, notify_payer) returns 201; tracker id = `{capture_id}-{tracking_number}`; default status SHIPPED; multiple trackers per capture allowed. PATCH `/status` works ONLY for CANCELLED (204) and is irreversible (CANNOT_PATCH_CANCELLED_TRACKER afterward); PATCH to ON_HOLD/SHIPPED/DELIVERED -> 400 INVALID_PARAMETER_VALUE; a `status` sent at creation is accepted but ignored. => PayPal CANNOT represent late/lost/delivered; carrier status must live in our DB; PayPal tracking is only a "tracking added" signal.
- Refunds: `POST /v2/payments/captures/{id}/refund` partial refund -> 201 COMPLETED; second partial refund OK; capture then reads PARTIALLY_REFUNDED; replay with same Request-Id returns the original refund (also if amount differs); real over-refund -> 422 REFUND_AMOUNT_EXCEEDED; reusing an `invoice_id` -> 422 DUPLICATE_INVOICE_ID; two concurrent identical refunds (same Request-Id) -> one 201 and one 409 (treat 409 as in-progress; reconcile by GET refund; never blind retry); `GET /v2/payments/refunds/{id}` works.
- Account notes: the app is a Merchant-type REST app on an India-based sandbox business account; USD orders worked. An India-based BUYER could not pay in USD; a US personal buyer worked.
- NOT yet tested (I): real return URL into our own server; refund returning PENDING; webhooks (design polls; webhooks are only a hint); Disputes API/simulator (may need special scope; optional); MCP tools from a backend (we use REST); buyer-side balance change; LLM cart reliability (target >=95% valid on a 20-prompt test).
- PayPal official MCP exists (`@paypal/mcp`, remote sandbox endpoints; tokens up to ~8 h) (V per PayPal docs read earlier) but we have NOT tested it from a backend. DECISION: build our OWN thin MCP server over the verified REST calls (only the tools we need), so it works from our services and doubles as the "agentic commerce" surface.
- Gated / do NOT use: Fastlane, Vault v3, Agent Ready, Store Sync, WebMCP, production Payouts.
